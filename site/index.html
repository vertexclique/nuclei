Each core completes its own IO.

Nuclei: proactive async runtime for Rust. A task hands its IO to the driver and gets the result back completed: no task waits for readiness and then makes the call itself. One shard per core, each with its own tasks, timers, buffers and driver.

Proactive, not reactive

A reactor tells a task when a socket is ready, and the task makes the call itself. Nuclei is a proactor: the task hands the operation over, and the result comes back to it.

The same read in both. The pictures count steps, not the time they take.

Completed by the kernel
On io_uring and I/O completion ports the kernel performs the read or the write, in memory the runtime keeps alive until the kernel is done with it.
The same contract on epoll and kqueue
There the shard’s driver makes the call: at once when the socket may be ready, otherwise on its next edge. The task only ever takes the result.
Into runtime memory
A read lands in a buffer of the shard’s pool and the task copies it out. read_owned and write_owned lend the driver your own buffer instead.

An echo server, one task per connection

No setup and no configuration: the first spawn or block_on starts a runtime with one shard per core.

use std::net::TcpListener;
use nuclei::Handle;

#[nuclei::main]
async fn main() -> std::io::Result<()> {
    let listener = Handle::<TcpListener>::bind("127.0.0.1:7000")?;
    loop {
        let (stream, _) = listener.accept().await?;
        nuclei::spawn(async move {
            let mut buf = [0u8; 1024];
            while let Ok(n @ 1..) = stream.recv(&mut buf).await {
                if stream.send(&buf[..n]).await.is_err() {
                    break;
                }
            }
        })
        .detach();
    }
}
#[nuclei::main]
Runs the async main in the runtime’s block_on. A Builder sets every setting for a runtime of your own.
Handle<TcpListener>
Takes std’s own listener and gives it async operations.
nuclei::spawn
Places the task on a shard, and there it stays.
recv and send
Complete for this task. On io_uring and completion ports the kernel completes them; on epoll and kqueue the shard’s driver makes the call.

The decisions underneath

  • io_uring first

    On Linux the runtime tries io_uring and falls back to epoll where the kernel, before 6.1, or a sandbox refuses it. The probe is safe even under a seccomp filter that kills a process for calling io_uring_setup. NUCLEI_BACKEND picks one by hand.

  • Thread per core

    A shard per worker thread runs its tasks and owns its driver, and on Linux each worker is pinned to its own core. A task stays on the shard it was placed on; nothing steals it.

  • Multishot receives

    On io_uring one receive stays armed for every arrival: the kernel fills a buffer of the shard’s pool as bytes come in, so a receive that waits holds no buffer of its own.

  • Nested block_on

    block_on works anywhere, inside a task too, and keeps its shard’s other tasks and IO going while it waits.

  • Descriptors you can trust

    A handle owns its descriptor. A registration ends before the descriptor closes, and kernel tokens carry a generation, so a reused descriptor number never receives another source’s events.

  • IO memory with a ceiling

    Each worker’s IO buffers hold at most 64 MiB unless you set otherwise. At the cap, IO waits for buffers to come back, so a worker’s IO memory never grows past it.

  • Cancel-safe IO

    Dropping a future halfway loses nothing. A read cut off by a timeout leaves the bytes the driver already took for the next read, and a lent buffer reaches the stream whole or not at all.

  • Vectored on every backend

    write_vectored gathers its slices into the write-behind in one call, all of them when it starts empty, on io_uring, epoll, kqueue and IOCP alike; read_vectored scatters what came in across yours. Streams and files both.

  • Workers that grow and drain

    A running runtime starts more workers, up to its maximum, with spawn_more_threads, and drains them with stop_thread: a stopped worker takes no new task and exits once its tasks are done.

  • Fairness counted, not timed

    Locks and semaphores let a caller take what is free even while others wait, so a release never waits for a sleeping task. A waiter passed over 16 times is owed a handoff: nobody gets in ahead of it, and the next release goes straight to it.

Modules

The pieces a server needs, in the one crate.

  • Sockets, files and pipes

    Handle<T>

    Takes std’s own types and gives them async operations and the futures-io traits.

  • Timers

    nuclei::time

    Sleeps, timeouts and intervals. Arming or cancelling a timer allocates nothing once the shard’s wheel has grown to fit.

  • Sync for any executor

    nuclei::sync

    Mutexes, reader-writer locks, semaphores, Notify, barriers, and mpsc, oneshot, broadcast and watch channels, on futures and wakers alone.

  • Child processes

    nuclei::process

    Spawn a child, wait for its exit and talk to it through async pipes.

  • Signals

    nuclei::signal

    Unix signals and Windows console events, as streams.

  • Runtime stats

    nuclei::stats()

    A snapshot of every shard: its tasks, polls, IO in flight, buffers, timers and errors by kind.

  • Local and blocking work

    spawn_local, spawn_blocking

    Tasks that are not Send run on the current shard; blocking work runs on a pool.

  • Attributes

    #[nuclei::main], #[nuclei::test], #[nuclei::bench]

    An async main, test or benchmark, run in the runtime’s block_on.

  • A short dependency list

    libc, kovan-*, futures-*

    libc on Unix, the kovan crates, futures-io and futures-core. The attribute macros need none of their own.

Checked, not assumed

The concurrent protocols are model-checked, the arithmetic under them is proved, and the suite runs on every backend.

  • TLA+ models

    The concurrent protocols: the task’s state machine, the park and wake handshake, an IO source’s sides and registrations, the ring’s operations, the sync primitives’ queues. Configurations that must pass sit beside mutations that must break them.

  • Lean proofs

    The arithmetic those protocols rest on: state words, counts and generations, for every size and every sequence of operations.

  • AddressSanitizer

    The suite under AddressSanitizer and LeakSanitizer, on io_uring and on epoll, in CI.

  • Every backend in CI

    io_uring and epoll on Linux 6.1, 6.6 and 6.12, kqueue on macOS, and completion ports on Windows.

proofs/README.md says what each model checks and what it leaves out.
