Moving from a readiness-based runtime

Most of what you write today has a direct counterpart. The table maps the usual patterns; the pitfalls below are the places where the same-looking code behaves differently.

Pitfalls

Dropping a task cancels it

The single most common bug after a move. A spawned task whose Task is dropped stops at its next await, and never runs if it had not started. Every fire-and-forget spawn needs .detach().

A write is accepted, not delivered

A write returns once its bytes are copied into the stream’s write-behind. Code that wrote and then exited, or wrote and then dropped the stream while expecting an error right away, should flush().await (or close().await). Bytes written behind are still delivered after a drop, for up to 60 seconds.

No work stealing

A task stays on its shard. A task that computes for a long time without an await holds every other task of that shard, and no idle core takes them over. Move such work to spawn_blocking, or break it up with awaits.

Buffers are copied, unless you lend them

recv and read copy from the shard’s buffer into your slice; writes copy into the write-behind. Where the copy matters, read_owned and write_owned hand the driver your Vec<u8> and give it back. See Proactive IO.

Configure io_uring before any IO

Proactor::with_config runs once, before the first IO, spawn or block_on; it panics otherwise. Configure from a plain fn main, then enter the runtime with block_on.

blocking_ methods inside a task

The blocking_ forms of the sync types run a nested block_on when called on a Nuclei shard, so the shard keeps running its other tasks. That is safe, but an .await is still the better call inside async code.
