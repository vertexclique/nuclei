Chapter 4 of 12

The proactive model

Nuclei completes IO for the task that asked. What that means, backend by backend, and what it changes in the code you write.

In this chapter

  3. 04.03Lending a buffer
  4. 04.04When a write is done
  5. 04.05Dropping a future halfway

Readiness and completion

A reactor tells a task when a socket is ready, and the task then makes the read or write call itself. If another reader got there first, or the readiness was spurious, the call would block, and the task waits again.

Nuclei is a proactor. A task hands its operation to its shard’s driver, and the operation completes for that task. No task waits for readiness and then makes the call itself. Every call on a descriptor is the driver’s, made into memory the runtime owns.

BackendHow an operation completes
io_uringThe driver submits it to the shard’s ring and the kernel performs it.
I/O completion portsIt is issued as an overlapped call; the kernel completes it and the shard takes the completion from its port.
epoll, kqueueThe driver makes the call: at once when the socket may be ready, otherwise on its next edge.

The task’s side is the same on all four: it asks, and later takes the result.

Where the bytes go

The kernel may hold an operation’s memory long after the task that asked has moved on, so Nuclei never lends the kernel memory a future borrows. Instead:

  • A read lands in a buffer of the shard’s pool, and recv (or read) copies it into the slice you passed.
  • A write is copied into the stream’s write-behind buffer and accepted at once; the driver writes it out as the socket takes it, in the order it was written.
  • Owned buffers: read_owned and write_owned take a Vec<u8> and give it back with the result, so the kernel reads into it or writes from it with no copy.

Each worker’s pool is bounded by Builder::io_buffer_cap (64 MiB by default). At the cap, IO waits for buffers to come back, so a worker’s IO memory never grows past it.

Lending a buffer

read_owned reads into the spare capacity of the vector, after the bytes it holds, and gives it back with how many bytes came (zero at the end of the stream, or when the vector has no spare capacity). write_owned writes all of the vector and ends once the kernel took the last byte. Both exist on Handle<TcpStream>, Handle<UnixStream> and Handle<File>.

When a write is done

Because a write is accepted into the write-behind, a successful write means the bytes are Nuclei’s to deliver, not that the kernel has them. flush waits until the kernel took every byte and reports a write that failed; close flushes and then shuts the write side, so the peer sees the end of the stream.

A write that fails keeps its error: every later write fails with it until a flush reports it. Bytes written behind are delivered whatever happens to the handle, as std’s are: get_mut and into_inner wait until the kernel took them, and a handle dropped before that leaves them to a copy of its descriptor, which delivers them for at most 60 seconds and then closes.

Dropping a future halfway

Async code drops futures all the time: a timeout fires, a cancellation token trips, a select takes another future first. Nuclei keeps the bytes safe when that happens:

  • A read whose future is dropped leaves what the driver already read for the next read, so nothing the kernel handed over is lost.
  • A lent read (read_owned) whose future is dropped hands the bytes read into its buffer to the next read, ahead of anything read after them.
  • A lent write (write_owned) whose future is dropped reaches the stream whole or not at all: withdrawn if none of it went out, finished by the driver if some did. On Windows a TCP write is always finished.

One receive for every arrival

On io_uring a stream keeps one multishot receive armed for every arrival: the kernel fills a buffer of the shard’s receive group as bytes come in, so a receive that waits holds no buffer of its own. A listener’s accept_multi works the same way for connections. The receive group’s size is set with recv_buffers and recv_buffer_size in the io_uring configuration (Production); a receive that runs past its share is paused until its reader catches up.
