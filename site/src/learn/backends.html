How the backend is picked

The first of these that says something decides, when a runtime's first shard starts:

  1. NUCLEI_BACKEND, when set and not empty: auto, io_uring, or the platform's poller by name (epoll, kqueue, iocp).
  2. The runtime's own Builder::backend.
  3. NucleiConfig::backend, the process's choice for every runtime that names none.
  4. auto: io_uring where the kernel lets the process have the rings its shards use, the platform's poller otherwise.

A backend named in any of these ways that the process cannot have fails with the reason; it never falls back. Proactor::backend() says which one the calling thread's shard runs.

io_uring

  • Linux and Android 6.1 or later, with the iouring feature (on by default). The ring is Nuclei's own, on libc alone.
  • The probe is safe even under a seccomp filter that kills a process for calling io_uring_setup; where io_uring is refused (an older kernel, a container's policy), auto runs epoll.
  • Each shard owns one ring, used by its own thread alone: single issuer with deferred task work, unless a kernel submission thread is configured (sqpoll_wake_interval).
  • A stream keeps one multishot receive armed, and accept_multi one multishot accept, filled from the shard's receive group (recv_buffers, recv_buffer_size).
  • Regular files are read and written with ring operations at the handle's cursor.

epoll

  • Linux, Android and illumos. On Linux it is what auto picks where io_uring cannot be had.
  • A readiness poller: the shard's driver makes each call when the descriptor may be ready, into the shard's buffers. Your code sees the same completion API.
  • Regular files run as pread and pwrite jobs on the blocking pool. A child's exit comes through its pidfd.

kqueue

  • macOS, iOS, FreeBSD, NetBSD, OpenBSD and DragonFly.
  • A readiness poller, served like epoll; a child's exit comes through EVFILT_PROC, wakes through EVFILT_USER.
  • Regular files run on the blocking pool.

I/O completion ports

  • Windows. One completion port per shard; operations are overlapped calls the kernel completes.
  • A handle takes std's TCP and UDP sockets, files, and a child's pipes. There are no Unix sockets on Windows.
  • A pipe or console opened for synchronous IO cannot complete on a port, so its calls run as jobs of the blocking pool and come back to the shard like the kernel's completions.
  • A TCP write, once issued, is always finished: a cancelled send there may have handed bytes to the network stack while saying it took none.
  • Timed waits use a high-resolution waitable timer where the system offers one, so timers are not rounded to the 15.6 ms system tick.

What is tested where

CI runs the suite on io_uring and on epoll on Linux @@CI_KERNELS@@ and on the runner's own kernel, on kqueue on macOS, and on completion ports on Windows; it runs it under AddressSanitizer on both Linux backends. The examples on these pages run on Linux, on io_uring and on epoll.
