A spawned task never ran, or stopped halfway

No message at all: the Task was dropped, and dropping a task cancels it. A loop that spawns per connection and throws the handle away cancels every connection at once.

Fix: call .detach() on tasks nobody waits for, keep them in a JoinSet, or keep the handles and await them. See Tasks.

the task has no output

the task has no output: it was cancelled or its runtime shut down before it completed, or it was awaited again after completing

A Task was awaited where it has no output to give: it was aborted, or its runtime was dropped before it completed.

Fix: keep the runtime alive until its tasks are done, or await task.join() (a JoinError says why) or task.fallible() (None) instead.

names no backend of this platform

the default runtime could not start: NUCLEI_BACKEND=kqueue names no backend of this platform (use auto, epoll or io_uring)

NUCLEI_BACKEND holds a name this system has no backend for. The message lists the names that work here.

Fix: set one of the names listed, or unset the variable.

asks for io_uring, but

the default runtime could not start: NUCLEI_BACKEND=io_uring asks for io_uring, but this build has no io_uring; leave it unset to use the poller

io_uring was asked for by name (NUCLEI_BACKEND, Builder::backend or NucleiConfig) and this process cannot have it; the reason follows but. Here the crate was built without the iouring feature; elsewhere it may be the kernel or a sandbox refusing the ring. A backend named by hand never falls back.

Fix: leave the backend unset, so auto picks io_uring where it can; turn the iouring feature back on; or run where io_uring is allowed (Linux 6.1 or later, and a sandbox that permits it).

the proactor is configured already

the proactor is configured already: call `with_config` once, before any IO

Proactor::with_config was called twice, or after the first IO, spawn or block_on, which configures the defaults.

Fix: call it once, first thing in a plain fn main, then enter the runtime with nuclei::block_on, as in Production. Under #[nuclei::main] the body already runs on the runtime.

the default runtime is already running

the default runtime is already running

Builder::build_global returned this: a free function, the attribute or an earlier build_global started the default runtime first.

Fix: call build_global before anything spawns, or build a Runtime of your own and use its methods.

block_on is nested too deep

block_on is nested 2 deep on one thread, the most allowed: each level runs on the thread's stack (raise the limit with `Builder::max_nesting`)

(Here the limit was set to 2.) Each nested block_on runs on the thread's stack, and one level past the limit panics before the stack would overflow.

Fix: await instead of nesting where you can; raise Builder::max_nesting where you cannot.

block_on never returns

No message: a task called block_on on a future that waits for that very task. The task is not polled again until the call returns, so neither can finish.

Fix: inside a task, wait for the other work with .await, not with block_on.

Data seems lost, or an error came late

Writes are taken into the stream's write-behind and sent by the driver, so a failed write can surface on a later write or on flush.

Fix: flush().await (or shutdown().await) where you need to know the bytes reached the kernel. See How it works.

A call of your own answers ResourceBusy

try_io or async_io on a socket found bytes the handle had read ahead: a read of your own would skip them.

Fix: read what the handle holds first (try_read until WouldBlock), then make your call. See Readiness.

A child's wait fails with ECHILD

Something other than Nuclei reaped the child: the program ignores SIGCHLD, or calls waitpid itself.

Fix: leave SIGCHLD at its default and let Child::wait reap your children.
