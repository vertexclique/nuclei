Whole files

nuclei::fs mirrors std::fs, with each call a future: read, read_to_string, write, copy, rename, remove_file, metadata, try_exists and the rest take a path and do the whole job.

Opening a file

A File is std's file in a Handle: File::open reads, File::create writes (creating or cutting the file), File::create_new creates a file to read and write and fails if it exists, and OpenOptions sets the rest (append, truncate, the mode and the open flags on Unix). A file reads and writes through the IO helpers and has a cursor that seek moves.

  • flush waits until the system has the bytes written behind; sync_all and sync_data put them on the device (Surviving a crash).
  • metadata, set_len, set_permissions, set_times and set_modified work on the open file; try_clone gives a second handle with a cursor of its own.
  • A read at the cursor sees the changes made beside it: bytes it read ahead before a positional write, a cut by set_len, an allocate or a copy into the file are never handed out after the change.

Lending buffers

As on streams (How it works), read_owned and write_owned take your buffer and give it back, so no byte is copied. The buffer is a Vec<u8>, an AlignedBuf, or a type of your own (IO utilities).

Reads and writes at an offset

read_at and write_at read and write at an offset you give, on a shared reference to the handle, so any number of tasks may use one file at once. They never read or move the cursor. read_exact_at and write_all_at do the whole length, and read_at_owned and write_at_owned lend your buffer.

  • A positional call lands after every write accepted at the cursor before it, and a read sees every positional write that returned before it. Two positional writes running at once land in either order, as two threads' pwrite calls do.
  • A positional write whose future is dropped still lands, and every later call of the handle waits for it.
  • read_at and write_at go through a buffer of the runtime's pool, at most 64 KiB a call; the owned forms use your buffer itself.
  • read_many_at makes many reads in one call and gives each buffer back in order with its result. On io_uring they go to the kernel together, at most 64 out at once.
  • These are the async calls, and they shadow std's FileExt::read_at and write_at, which the handle reaches through Deref and which block the worker. std's stay reachable as (*file).read_at(..).

Surviving a crash

sync_all writes the file's data and metadata through to the device, and sync_data its data, once every write accepted before the call landed. A file's sync does not cover its name in its directory; fs::sync_dir does. To replace a file so a crash leaves the old contents or the new and never a mix, write a temporary file in the same directory, sync it, rename it over the target, then sync the directory.

Once a sync of a handle failed, every later sync of it fails with the same error, since the system reports a lost write-back only once. Open the file again to start over.

Space, write-back and copies

allocate changes the space a range of the file uses, as its Allocate mode says: Extend reserves it and grows the file, KeepSize reserves it and keeps the length, PunchHole frees it, and ZeroRange makes it read as zeros. A system that cannot do a mode answers Unsupported: macOS cannot zero a range in place, and FreeBSD cannot reserve space past the end of a file without growing it, so its KeepSize takes a range inside the file. A file system may refuse a mode with its own error (FreeBSD's ZFS reserves no space), and on FreeBSD one that cannot free a range (UFS) writes zeros over it for PunchHole.

sync_range writes a range back and waits for it; it writes no metadata, so it is not a durability guarantee. copy_range_to copies a range into another file, in the kernel where the system can, in chunks of at most 16 MiB, and moves neither cursor.

Locks

lock_file takes an advisory lock on the whole file, shared or exclusive, and waits for it on the blocking pool so the worker runs on. A future dropped while it waits never leaves the file locked with nobody to release it. try_lock_file answers at once, with WouldBlock when another holder has the lock, and unlock_file releases it once the writes before it landed.

std's own lock, try_lock and unlock stay reachable through Deref; std's lock blocks the worker while it waits.

Direct IO

A file opened for direct IO (O_DIRECT on Linux, FILE_FLAG_NO_BUFFERING on Windows) skips the system's page cache. Nuclei reads and writes it with exactly your lengths and offsets, with no read-ahead and no write-behind, so the kernel's alignment rules apply to your calls as they would to your own system calls: the memory's address, the offset and the length are multiples of the device's block size. AlignedBuf gives memory at the alignment you ask for.

Directories

create_dir, create_dir_all and DirBuilder (recursive, with a mode on Unix) make them; remove_dir and remove_dir_all take them away. read_dir streams the entries a page at a time, so a directory of any size is read without holding it all.

Links: hard_link, read_link and canonicalize, symlink on Unix, symlink_file and symlink_dir on Windows.

Where file IO runs

A regular file is always ready to the kernel, so no poller can say when its IO would wait. On io_uring a file's reads and writes, at the cursor and at an offset, its syncs, sync_range and allocate are operations of the shard's ring; on the other backends each is a job of the blocking pool. Calls by path, lock_file, copy_range_to and the file's other calls run on the blocking pool; try_lock_file runs on the calling thread, since it never waits. On Linux, File::open opens a regular file on a local file system on the calling thread when the kernel's caches resolve its path at once (openat2 with RESOLVE_CACHED, Linux 5.12), with no job; any other open, a FIFO, a device or a file on a network file system among them, goes to the blocking pool. A File that is not a regular file (a FIFO, a terminal, a pipe) is a byte stream the driver serves like a socket.
