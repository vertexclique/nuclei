Reads and writes as futures

Streams implement the futures-io traits (AsyncRead, AsyncWrite, AsyncBufRead, AsyncSeek), so code written against them works unchanged. nuclei::io adds the calls you await, in four extension traits:

TraitCalls
AsyncReadExtread, read_exact, read_to_end, read_to_string, read_buf, read_u32 and every number (big-endian, or _le), take, chain
AsyncWriteExtwrite, write_all, write_vectored, write_u32 and every number, flush, shutdown
AsyncBufReadExtread_line, read_until, lines, split, fill_buf, consume
AsyncSeekExtseek, rewind, stream_position

Lines and buffers

BufReader puts a buffer in front of a reader, so small reads and line reads take from memory; BufWriter gathers small writes into one; BufStream is both, for a stream that reads and writes.

Copies

io::copy moves everything a reader gives into a writer, then flushes; copy_buf does it from a buffered reader's own buffer. copy_bidirectional runs both directions between two streams at once, the heart of a proxy, and answers the bytes moved each way.

Buffers you lend

The owned calls (read_owned, write_owned, write_zero_copy, and the datagram and file forms) lend the driver your buffer and give it back, so the kernel reads into and writes from your memory and no byte is copied (How it works). A write takes any IoBuf and a read any IoBufMut, and each gives back the same type: a Vec<u8> in, a Vec<u8> out.

  • AlignedBuf is a buffer of a fixed capacity at an address of the alignment you choose, made by a safe constructor (new or zeroed): the buffer for a file opened for direct IO. Its memory is yours, not charged to the runtime's io_buffer_cap.
  • A type of your own (a shared byte buffer, memory of a registered region) implements the two traits. They are unsafe: the memory must stay in place while the runtime holds the value, even when the value moves.
  • The runtime keeps a Vec<u8> or an AlignedBuf as it is while a call has it, and boxes a buffer of any other type once.
  • Where the compiler cannot see the buffer's type, write it: Vec::<u8>::new(), not Vec::new().into() or Default::default(), and send_to_owned::<A, _> where you name the address type.

Several buffers in one call

write_vectored_owned writes every buffer of an IoVecBuf in order as one write: no other write of the handle comes between two of them. read_vectored_owned fills the room of each buffer of an IoVecBufMut before the next one's. Both take a Vec or an array of any owned buffer type and give the buffers back together. TCP and Unix streams, pipes and files have both.

Each call of the kernel takes every buffer at once: writev and readv, or a sendmsg and recvmsg of several buffers, on epoll and kqueue; their ring operations on io_uring; a WSASend or WSARecv of several buffers on I/O completion ports; pwritev and preadv for files. A call the kernel takes part of goes on from the byte it stopped at. Where the system has no vectored call of the kind, the buffers go one call each, in order: a buffered file on Windows does so, and a Windows handle that is not a socket writes that way and reads into its first buffer only.

In memory

Streams with no socket behind them, for tests and for joining parts of a program:

  • duplex(n): two connected streams, n bytes of buffer each way. simplex(n): one pipe, a reader and a writer.
  • io::split(stream): a read half and a write half of any stream, put back with unsplit.
  • empty(), repeat(byte), sink(): a reader at its end, a reader without end, a writer that keeps nothing.

The standard streams

io::stdin(), io::stdout() and io::stderr() are the process's own, as async streams.

Any std object

The socket and file types are Handles over std's own objects, and Handle::new takes over any other one: on Unix anything with a file descriptor, on Windows sockets, files and a child's pipes. get_ref reaches the object; into_inner gives it back once the bytes written behind went out.
