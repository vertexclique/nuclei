Pitfalls

Dropping a task cancels it

The most common bug after a move. A task whose Task is dropped stops at its next .await, and never runs if it had not started. Every fire-and-forget spawn needs .detach(). See Tasks.

A write is taken, not delivered

A write returns once its bytes are copied into the stream's write-behind. Code that writes and then exits, or expects an error right away, should flush().await or shutdown().await. See How it works.

No work stealing

A task stays on its shard. One that computes for long without an .await holds every other task of that shard, and no idle core takes them over: give such work to spawn_blocking, or break it up.

Buffers are copied, unless you lend them

recv and read copy from the shard's buffer into your slice; writes copy into the write-behind. Where the copy matters, read_owned and write_owned lend the driver your vector.

Configure io_uring before any IO

Proactor::with_config runs once, before the first IO, spawn or block_on; it panics otherwise. Configure from a plain fn main, then enter the runtime.
