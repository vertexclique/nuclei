Running a program

nuclei::process::Command is shaped like std's: arguments, environment, working directory and standard streams, then output (collect what it printed), status (only the exit) or spawn (a Child to talk to). The examples run Unix programs.

A shard's driver watches each child's exit (a pidfd on Linux, a process event on kqueue, a wait on the process handle on Windows) and reaps it, so a wait holds no thread, and a child whose Child was dropped leaves no zombie behind.

Talking to a child

Piped streams are async: write to stdin, read stdout and stderr with the IO helpers. Dropping stdin ends the child's input; wait closes it first too, so a child that reads to the end can exit.

Ending a child

  • kill().await ends the child (SIGKILL on Unix, TerminateProcess on Windows) and waits for its exit; start_kill() only starts it.
  • kill_on_drop(true) ends the child when its Child is dropped before it exits. By default a dropped child runs on.
  • try_wait() gives the status if the child exited, without waiting.
  • For what Command does not mirror, as_std_mut reaches std's command underneath, spawn_with starts the child through your own code, and into_std takes std's command back.

Ctrl-C

nuclei::signal::ctrl_c() completes when the process gets a Ctrl-C: SIGINT on Unix, the console's CTRL_C_EVENT on Windows. Listening starts with its first poll, and replaces the default action, which would end the process.

Unix signals

signal::unix::signal(kind) listens to one signal from then on, as a stream: recv().await ends once it was delivered, once or more, since the last recv. SignalKind names the usual ones (hangup, terminate, user_defined1, ...) and from_raw any other.

Windows console events

signal::windows has ctrl_c, ctrl_break, ctrl_close, ctrl_logoff and ctrl_shutdown, each a CtrlEvent whose recv().await ends at the next such event.
