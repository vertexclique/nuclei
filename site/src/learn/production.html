Every runtime setting

Every setting is optional, and an unset one takes a default that needs no configuration to work well. Set them on a Builder, then build a runtime of your own or build_global the default one (Runtime). build checks them all before it starts a thread: a value outside what the runtime can work with fails with InvalidInput naming the setting, its value and the range it must be in (Errors).

A busy worker looks at its timers and IO every event_interval task runs, and also, checked every 16 runs, whenever its last look is more than a millisecond old, so a run of slow tasks cannot keep IO waiting for long.

Hooks

A runtime calls hooks of yours on its threads and around its tasks: for metrics, tracing or thread setup. Each task hook is given the task's Id.

A hook runs in the middle of the runtime's work: keep it short. A thread hook that panics loses nothing: the panic is caught where the runtime calls it, once the panic hook reported it, and the thread goes on with the shard, tasks or jobs it holds. So is a panic of thread_name_fn where the runtime starts a thread of its own accord (a blocking-pool thread, a runner for a shard the handoff took), the thread then taking the default name; one as a worker starts reaches build or spawn_more_threads before anything is claimed. A task hook must never panic: one that does aborts the process, as it runs in the middle of a task's change of state. Task hooks get a TaskMeta: the task's id(), and its name() when task::Builder gave one.

on_long_poll finds the task that holds a worker up: it is called, on the watch's own thread, for each poll that runs past handoff_after (Tasks).

The io_uring configuration

The rings are configured once per process, before any IO, with Proactor::with_config: every runtime starts from these settings. A second call, or one after IO has started (which configures the defaults), panics. Builder::io_uring gives one runtime's workers ring settings of their own instead, and build answers a setting a ring cannot work with as an error rather than a panic.

Four presets fill the struct from a queue length: interrupt_driven (the one to pick when unsure), low_latency_driven and kernel_poll_only (a kernel submission thread), and io_poll, whose ring takes only the reads and writes of files opened with O_DIRECT: a file's syncs, sync_range, allocate and a buffered file's reads and writes, which the kernel refuses there, are made on the blocking pool. NucleiConfig::backend is the backend of every runtime that names none.

The sizes are checked where they take effect: queue_len at least 64, recv_buffers 0 or a power of two below twice queue_len, and recv_buffer_size from 512 bytes to 1 GiB while there are receive buffers. A value outside fails the first runtime built with it, with InvalidInput naming the setting.

Counters

nuclei::stats() takes a snapshot of every shard alive in the process (each runtime's workers, then the shard of each thread in block_on) and of the blocking pools; Runtime::stats takes one of a single runtime's workers and pool. It reads the shards without stopping them; most counts are published by a shard as it is about to wait for work, and by a busy one every few hundred task runs.

Stats also has blocking_threads and blocking_queue_depth, off_shard_errors for IO run on threads that run no shard, and receive_buffers_missing for shards that started without the io_uring receive buffers they asked for.

IO counts and latencies

A runtime built with record_latencies(true) keeps a log2 Histogram of how long each task poll ran, in ShardStats::poll_times. With the io-stats feature (Setup) it can also count and time each worker's IO:

  • Builder::count_io(true) fills ShardStats::io, an IoCounts: reads and writes with the bytes of each, and accepts.
  • record_latencies(true) also fills ShardStats::io_latencies, an IoLatencies: the time from submission to completion of reads, writes, accepts, connects and file calls. On epoll and kqueue it is None: the driver makes each call once the kernel says it is ready, so there is no wait in the kernel to time.

Without the feature, no IO path carries counting or timing code, and these items do not exist. With it, every IO call costs a few instructions, counted or not, so leave it off where nobody reads the counts. The API reference here is built with io-stats on, so it lists them; they exist only with io-stats on.

A clean shutdown

A server stops taking connections when asked, lets the open ones finish, and gives up after a deadline. A CancellationToken carries the request to every task, Ctrl-C raises it, a JoinSet holds the connections, and timeout bounds the drain.

Tests

#[nuclei::test] makes an async test: its body runs in block_on on the default runtime, or on a runtime of its own with threads = N or start_paused = true (paused time). A test may return a Result, like any test.

#[nuclei::bench] does the same for a benchmark on the nightly test harness.

The earlier entry points

Programs written against earlier versions set up the default runtime with init or init_with_config; both still work, on the shards. GlobalExecutorConfig sets the workers to start (with_min_threads, or from an environment variable with with_env_var), the most to run (with_max_threads) and their names. spawn_more_threads starts more workers, up to the maximum (none once the runtime's drop took its threads), and stop_thread drains one: it takes no new task and exits once its tasks are done.

Code that drove the proactor by hand still can: Proactor::get().wait(max_events, timeout) drives the calling thread's shard once, and wake ends every wait in progress.
