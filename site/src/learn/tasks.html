Spawn and await

nuclei::spawn takes a future that is Send + 'static and returns a Task<T>. A task is a future itself: awaiting it gives the task's output. If the task panics, awaiting it resumes the panic.

Dropping, detaching, cancelling

A Task owns its task: dropping it cancels the task. To let a task run on with nobody waiting for it, call detach.

CallWhat it does
detach()The task runs to its end; its output is dropped.
cancel().awaitCancels and waits until the future is dropped; gives the output back if the task had finished.
abort()Cancels without waiting. abort_handle() gives an AbortHandle that does it from anywhere and outlives the task.
is_finished()Whether the task completed or was cancelled.

The most common surprise

A server loop that spawns a task per connection and drops each handle cancels every connection at once. Write nuclei::spawn(handler).detach(), or keep the tasks in a JoinSet.

Why a task gave no output

Awaiting a task panics where it has no output to give. join() gives a Result instead: the output, or a JoinError that says the task was cancelled or panicked (with the panic's payload). fallible() gives an Option.

Many tasks: JoinSet

A JoinSet holds tasks and gives their outputs in the order they finish. Dropping the set cancels whatever is still in it, so no task outlives the code that owns it.

join_next_with_id says which task finished, try_join_next never waits, join_all collects every output, and abort_all, detach_all and shutdown end or release them all.

Ids and names

Every task has an Id, unique in the process and never reused: task.id() from the handle, task::id() from inside it, and the task hooks are given it too. task::Builder spawns with options and answers an io::Result: a name, which the hooks read with TaskMeta::name, and a worker to place the task on (Runtime).

Tasks that are not Send

nuclei::spawn_local takes a future that need not be Send and keeps it on the calling thread's shard. There is no local set to create first.

Work that blocks

A blocking call (a synchronous library, a long computation) would hold its shard and every task on it. nuclei::spawn_blocking runs a closure on the runtime's blocking pool instead and returns a Task for its result. The pool grows on demand up to max_blocking_threads, and idle threads leave after thread_keep_alive.

A poll that blocks anyway

Blocking code finds its way into tasks: a lock of a synchronous library, a slow system call, a loop longer than planned. When one poll of a task runs past handoff_after (10 ms by default), the task holds up only itself: its worker's shard, with every other task, timer and IO of it, goes on on another thread on the same core, and the blocked task carries on once its poll returns. A task placed on a worker stays on that worker through it.

  • The blocked thread still shares the core, so a handoff is a rescue, not a place to run work: give long work to spawn_blocking or break it up with yields.
  • Tasks that spawn_local keeps on the blocked thread, and a nested block_on there, wait for it and finish on that thread. A shard_local! value they or the rest of the blocked poll use is lent back to each with by the shard's new thread, between two of its polls.
  • on_long_poll names the task that blocked (Production), and stats() counts each worker's handoffs and its longest_poll.
  • Watching costs each poll two plain stores and a load, and each call a task makes into its worker (a wake, a spawn, a send or a receive) two loads and two stores: on io_uring a 64-byte TCP round trip runs 10.8% more instructions with it, a spawn and its join 20% more. handoff_after(None) turns it off.

Task-local values

task_local! declares a key whose value belongs to one task: scope runs a future with it set, and any code that future runs reads it with get, with or try_with.

Yielding and the budget

Each poll of a task may complete a budget of operations (coop::BUDGET) before it yields, so one busy task cannot hold its shard. IO that completes spends one, and so does a receive, an acquire or a lock of nuclei::sync that completes without waiting, so a loop over a channel that is never empty yields too. A loop that awaits nothing else can spend the budget itself with coop::consume_budget(); task::yield_now() gives the other tasks a turn at once, and coop::unconstrained runs a future with no budget.
